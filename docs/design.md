# Ink Knight: design and tools

A Lichess client inside KOReader, built for e-ink. `ink_knight` is the plugin identifier. The research and the lessons from earlier clients are in `docs/research/chess-clients.md` and `docs/research/lichess-api.md`, in the `kindle` project.

## What is in and out

| Part | What it has |
|---|---|
| Play | Seek in rapid and classical with an optional rating range, correspondence, challenges with blitz or no time limit, the Lichess computer with a clock or no time limit, choice of color in a challenge, several games at once, a list with whose turn it is, the challenges sent and still unanswered, which can be canceled |
| During a game | Draw offers, draws by repetition, asking for a takeback, giving time, claiming when the opponent leaves, playing again |
| Train | Puzzles with a saved pile, puzzles by theme and by opening, the history of puzzles tried, the results of the last 30 days, the daily puzzle, a game against a small engine with no network |
| Review | Past games and favorites, with the evaluation, the most played moves and the tablebase result of each position, and the summary of the analysis of the site |
| Players | Search, who is online among those followed, profiles, follow and unfollow, a rating chart with statistics, the record against someone |

Out of scope, by decision: tournaments, bullet (the network alone takes 1.4 to 2.7 s per move on a Kindle), engine help in a game on Lichess, chat, Lichess TV, broadcasts, studies, importing PGN, and the bot API, which needs turning the account into a bot account. Variants stay as an idea for later, starting with Chess960, since each one needs its own rules. Lichess refuses a seek below rapid, so `Api.REAL_TIME_SEEK` only lists clocks of at least 8 minutes in the estimate it uses (initial time plus 40 times the increment), and a test keeps it that way. A correspondence seek has no way to be canceled through the API, because the cancel route only covers real-time seeks, and when an opponent cancels the game before the seek's author does, Lichess puts the seek back by itself (`AbortListener` in the Lichess source). So one seek can lead to several games in a row.

## Permissions

Each endpoint of Lichess accepts any one of its scopes, so `board:play` alone covers seeks, games, challenges, the computer and the event stream. The rest is by feature: `follow:read` and `follow:write`, `puzzle:read` and `puzzle:write`, `challenge:write` only to give time, and `preference:write` only to add or remove a favorite. That last one also allows changing the preferences of the account, which the plugin never does, so the link for creating a token leaves it unmarked. Listing favorites needs none of these.

`token_scopes.lua` knows what each feature needs. Lichess states the scopes of the token in the `x-oauth-scopes` header of every authenticated answer, and the plugin reads it from `/api/account`. `/api/token/test` gives the same, but its answer repeats the token, and answers go through a temporary file. A missing scope does not hide anything: the option stays and says what is missing, as a hidden feature looks like one that does not exist. When the header is absent nothing is assumed, and Lichess has the last word.

Token creation has a link with the scopes marked, in `ui/create_token_screen.lua`, shown as a QR code.

## Network

- **A child process per connection.** Each request runs in a child made by KOReader's `runInSubProcess`, using LuaSocket and LuaSec, which come with KOReader on every platform, so there is nothing to install. A TLS handshake in the main process would freeze the interface for seconds at each move. The child writes to its own files, and `Net:tick` reads them without waiting. The child, the connection and the files are the ones of `https_request.lua`, `tls.lua` and `https_main.lua`, shared with the other Beater Studios plugins (pattern https); `net.lua` adds the queue, the streams and what Lichess asks for.
- **macOS, for development only.** macOS kills a forked child that touches the network ("crashed on child side of fork pre-exec"), so there each request runs as a new program, through `https_main.lua`, with the request in a file readable only by the user, which the program deletes on reading. Devices run Linux and always use the forked child.
- **Certificates and the name of the server.** `tls.lua` opens every connection with TLS 1.2 or newer, asks for `verify = "peer"` with KOReader's `data/ca-bundle.crt` and then checks the name of the server against the alternative names of the certificate. KOReader's `ssl.https` is not used, because on the stable version (2026.07.2) it leaves verification off by default and never checks the name, so any valid certificate, for any site, would get the token. Recent builds do check it, which is why this passed on a newer emulator and failed on a real Kindle. A proxy set in KOReader is ignored, and a redirect is never followed. `tools/koreader/check_https.lua` confirms each refusal for the right reason with real connections, and it needs to run on the oldest version supported, not only on the emulator.
- **Streams** write each piece to a file as it arrives, read by offset and split into lines. Empty lines are keep-alives. A connection silent for 10 minutes ends and reconnects.
- **Checking costs little.** On a Kindle, a file operation right after a pause takes 5 to 30 ms, against 0.05 ms in a tight loop, so what matters is how often the screen checks. It checks once a second while only streams are open, and three times a second while a request is running. A new request brings the next check forward, so it starts right after the screen paints the tap. Each check asks the size of the file of a stream and opens it only if it grew, and asks the system whether the child ended, so there are no extra files to look for.
- **One at a time.** Lichess asks for one request at a time, so they run in a queue, with a 45-second limit each, and streams run beside it. A 429 pauses the queue for a minute.
- **Children are always collected.** A child that ends or dies is noticed even if it wrote nothing, and is reaped, so none stays as a zombie. Closing kills them all and waits.
- **Token in use.** On devices, it stays in memory and goes in a header, so it is not in the address, in temporary files or in the list of processes. Only letters, digits and `_` are accepted in a token, and only those plus `-` in ids and names.
- **Other servers.** The opening database at `explorer.lichess.org` asks for the token, and `net.lua` only sends it there and to `lichess.org`. The tablebase at `tablebase.lichess.org` is public and never gets it. The server of each address is read by `Request.host`, the same way LuaSocket reads it, so an address like `https://lichess.org:x@evil.com/` is `evil.com` and gets nothing.
- **Moves are never sent twice by itself.** If a move fails, the board goes back and says so, and the reader decides.

## Where the token is kept

The shared storage of an e-reader is a FAT-like filesystem, where `chmod` does nothing, so a file there is readable by anyone who plugs the device into a computer. `token_store.lua` therefore:

- On a Kindle, uses `/var/local/ink_knight`, in the system partition, which USB does not reach, with folder `700` and file `600`.
- Everywhere else, uses `settings/ink_knight_token`, also with `600`.
- Writes under `umask 077` to a temporary file and renames it, so the file is never readable by others, not even briefly.
- Checks the permissions the filesystem really reports, and reads the file back, before calling it protected. Otherwise it falls back to the settings folder and warns the reader, and **Where the token is** in the settings says which case applies.
- Moves a token found in the settings folder to the private place, and removes the old file.
- Closes the permissions again whenever it loads a token. At every boot, a Kindle gives the group `javausers`, used by its own services (`framework` and `bluetooth`), access to the whole system partition, which turns the folder into `2770` and the file into `660`. Other users never get access. So, from a reboot until Ink Knight is opened, those services can read the token.

The token is not encrypted, because the key would have to live on the same device, which would only look like protection. What this does not protect against: anything running as root, including SSH and other plugins, can read it. The answer to those cases, and to a lost device, is revoking the token on Lichess, and the permissions are already limited so it cannot send private messages or change the account.

## Screens

`ui/home.lua` opens on a first page with no network: play online, or connect an account if there is no token, play offline, about and exit. Playing online asks KOReader for the Wi-Fi, opens the online part and starts the network, and leaving that part stops it. With no connection, that part stays open, says so, and tries again every 30 seconds. When Lichess refuses the token, on any request, every row of that part is disabled except one that goes to connecting an account, and tapping it removes the token, so leaving without connecting comes back to the first page asking for an account. Saved puzzles and the offline game are also reachable from the first page.

Every full screen opens in portrait, ignores rotation while it is open and gives the previous rotation back on closing, also when opening fails halfway: `portrait.lua` (pattern portrait), with each screen's setup in `setup` instead of `init`. The menu opens the first page under `pcall`, so a failure shows a notice instead of taking KOReader down, and the rows of a page, the board and the chart are drawn under `pcall` too, with a short message in their place and the way back still working. The Back key of devices with keys goes one step back (`onBack`); KOReader's own `Close`, sent to every window before it quits, only closes, and leaves the windows alone before powering off.

`ui/page.lua` is every screen outside the board: a title with a way back, and rows meant for a finger, such as tiles, toggles and stats. There are no popups from KOReader. A choice is a page, a question is a page with two buttons, and `ui/toast.lua` gives short notices at the bottom without taking taps. A row answers a tap by inverting, because what comes next can take a moment on e-ink. The exceptions are the keyboard, and the question that allows a phone on the token page. The challenges received and sent share one line when both exist, each a button of half the width whose text gets smaller if it does not fit, and each takes the whole line alone. The sent ones come from the event stream, which also reports the challenges the reader makes, so no other permission is needed, and canceling uses the same `board:play`. A correspondence seek cannot be listed or canceled through the API, so it is not among them. Both lists start over whenever the stream opens, after a sleep or a dropped connection, since Lichess sends everything still pending and nothing about what changed while it was closed. A player who is not signed in comes from Lichess with no name and is called anonymous.

While the device sleeps, nothing of the plugin is drawn and no timer runs: every timer of a screen (the minute clock, the network, the clock of a game, the engine, the reply of a puzzle, a notice that leaves by itself) goes through `sleep.lua` (pattern sleep), which holds it until the device wakes up and then runs it once. Without it, a timer that came due during the short wakeups of a sleeping Kindle drew over the sleep screen.

If the device sleeps with any screen of the plugin open and the KOReader sleep screen is set to the book cover, `assets/screensaver.png` shows instead. `ink_knight/screensaver.lua` wraps KOReader's `Screensaver.setup`: KOReader picks the image as usual, and the plugin swaps it only when the topmost full-screen window is named `ink_knight_*`, which covers every screen, new ones included. Nothing is saved, so closing the plugin brings back the book cover. Powering off, restarting or any other sleep screen mode are left alone. The image is 1200x1600, twice 600x800, so it stays sharp on larger screens; on 600x800 KOReader halves it.

## Board

- **Pieces** come from the chess symbols of FreeSerif, which ships with KOReader, so there is no art to license. The solid symbol gives the shape and the hollow one the outline: a white piece is the solid one in white with the hollow one in black, and a black piece is the solid one in black. Both are cut to the same box, so they stay aligned and centered.
- **Styles.** Five board styles: plain, with gray dark squares, and newspaper, crosshatch, dotted and contrast. The patterns are only black and white, and contrast uses the darker gray 0x55. On those four, a piece gets a white edge, its shape grown by 2 px, so it stands out. Three piece sets: classic, from FreeSerif, and Cburnett and Merida, pictures in `ink_knight/pieces` from the Lichess source (see NOTICE), drawn with KOReader's SVG renderer and kept for the session, so they are drawn once per size. A set whose picture fails to load falls back to classic. Coordinates are optional, in the corners of the edge squares. All of this is chosen in the settings and in the offline menu. A dark theme for the whole plugin was left out: KOReader's night mode already inverts it.
- **One screen for every mode.** `ui/board_screen.lua` only draws the state it receives and reports taps. `live_game`, `offline_game`, `puzzle_screen` and `review_screen` decide what to show.
- **The list of moves.** `ui/move_list.lua` shows a game in the usual notation, two moves to a row as on a score sheet, on a page that opens on the sheet holding the move to look at, the last one by default. `Chess.san_list` writes the notation from the starting position, so a game from a position is numbered from there. Writing a move lists the legal moves to tell pieces apart, about 20 ms for 160 half moves on a Mac and much slower on a Kindle, so the games keep what was written and add only the new moves, and the review uses the notation that comes with the game from Lichess. The offline game has it on its bar, the online game among its actions, and the review in its menu, where the move shown is marked and a tap on another goes to it. At the start of a review the list opens on its first sheet, and elsewhere on the last move. Puzzles do not have it, since they are a few moves from a position. The first row is the name of the opening (see Opening names).
- **Refresh.** `board_diff.lua` compares what is on screen with what comes next, and only what changed goes to the display: each square as its own region, so a move touches the squares it changed and nothing between them. A clock only touches its own bar, with `fast`, outside the count. The board opens with a full flash, and after 40 updates without one the whole screen flashes again, to clear what e-ink leaves behind: `refresh.lua` (pattern eink_refresh) counts them, since KOReader never counts `ui` updates towards its own periodic flash. The pages share one count of 8, as they open and close over each other with the same layout, so going back and forth does not flash each time; the plugin opening and closing over KOReader always flashes. Tried on the Kindle 10 in 2026-11: `[partial]` looked worse than `ui`, because it is sent as a full update and redraws the gray squares, and GL16 as a partial update brought no gain worth calling the driver directly. So squares stay on `ui`. DU4, which other Kindles can use, does not exist in the driver of this model, where waveform 7 is `ZELDA_LAST`.
- **Time and battery.** `ui/status_strip.lua` draws them centered at the bottom of every full screen. The room comes from the buttons of the board, which lost 8 px, and from the gap that was left under them, so the board keeps its size. `Home` has one timer for the whole plugin: when the minute changes, only the screen on top redraws, and only the middle of the strip goes to the display.
- **Staying awake.** Only during a game with a clock; correspondence does not need it. `awake.lua` (pattern awake) pauses KOReader's auto suspend and, on a Kindle, resets the idle timer of the system every 4 minutes, as a touch would. The power button keeps working: earlier versions used `preventScreenSaver`, which also made the Kindle ignore the button and outlived a crash; the first start of this version undoes what they may have left. While charging, the timer is not reset, as KOReader's own auto suspend does, so a game of more than about 10 minutes without a touch, plugged in, can be cut by the sleep screen. Other plugins with the same module share the device: it only sleeps again when the last one lets go. Inside Ink Knight each screen that needs it is its own holder (`Awake.set(on, self)`): the live game, the game between two people with a clock and the chess clock, so one letting go never lets the device sleep under another.

## Analysis

Only in `review_screen`, which only opens finished games, so nothing here can help in a game under way. A position asks three things, one at a time: the cloud evaluation, the most played moves and, with up to 7 pieces, the tablebase. The API has no way to ask Lichess for a new analysis, and the cloud only keeps positions already computed, so a position outside it says so. A game someone analyzed on the site also shows the evaluation of each move, read from the same export, and the export asks for the accuracy and the phases too (`accuracy=true&division=true`): More then offers the summary of the analysis (`Game.analysis_summary`), with the accuracy of each side when Lichess has it, its inaccuracies, mistakes and blunders and its average centipawn loss, and the moves where the middlegame and the endgame begin. The review also marks those moves, right after the move in the status line, since the line holds one line and its end is what gets cut, and the list of moves has a heading before their rows (`marks` in `MoveList`). A phase past the moves the review could read is not named.

## Rules

`chess.lua` is the whole set of rules, with no KOReader dependency, checked against known position counts (perft) on six reference positions. It covers castling, en passant, promotion, pins, checks, mate, stalemate, insufficient material, the fifty-move rule, the usual notation and UCI. Lichess remains the authority in online games: the local rules only decide what can be tapped, and the stream always replaces the local state. Variants other than standard are refused when a challenge is answered.

## Opening names

`openings.lua` names the opening of a game without internet, from the list Lichess publishes (`lichess-org/chess-openings`, CC0): 3,865 positions with their names, in `ink_knight/data/openings.lua`, 484 KB on the device and about 60 KB in the zip. As on Lichess, a game is named after the last position of the list it went through, so another order of moves reaching the same position gets the same name, and the name stays once the game leaves the list. A position is the first four fields of its FEN, with the square passed over only when taking on it is possible (`Chess.epd`), as Lichess writes them; the same text counts repetitions. The list goes up to 36 half moves, so a lookup plays at most that many. It is read the first time a name is asked for, in about 3 ms on a Mac and 43 ms on the Kindle 10, and takes 672 KB there. Only games from the usual start have a name. The names are in English in the three languages, as on the site.

The name is the first row of the list of moves, in the game against the engine, between two people and in the review. A review of a Lichess game uses the name that came with the game, so the list agrees with the start of the review even after Lichess changes its list, and looks it up only when the game came without one. In a Lichess game it only shows once the game is over: Lichess does not send it to the players during a game, only to spectators and to the analysis, and Ink Knight does the same.

The data is generated, following the project's rules for third-party data: `tools/openings/fetch_sources.sh <empty folder>` downloads the five files at a fixed commit (`3ba6b20`), refuses a folder with files and checks each one against `tools/openings/sources.sha256`, and `luajit tools/openings/build.lua <folder>` reads every line of moves with the plugin's own rules, so the positions are the ones it will look up, and stops on a move it cannot read or on two names for the same position. The release builds the file again and fails if it differs from the repository. Updating the list is a change of its own: a new commit in the script and new checksums, with the difference in the names reviewed. There is no list of approved items, since nothing is chosen for the reader, as a word of the day would be.

## Puzzles

A batch of 15 is saved in `settings/ink_knight.lua`, and another is asked for when 3 or fewer are left. Each theme has its own pile, and results go to Lichess under the theme they came from. Solving works with no network. Results stay saved until they reach Lichess, in the same request format as the batch API, and a failure just keeps them for next time. A puzzle counts as a win only with no mistake and without showing the move. The puzzles menu has a difficulty (`easiest` to `hardest`, relative to the reader's puzzle rating, `normal` by default) and a color to play (either, white or black), sent with each batch. The API documentation says the color only works for one puzzle at a time, but the server, `PuzzleBatch.scala` in lila, draws three times as many and keeps that color for a batch too. Each puzzle keeps what its batch was asked with (`wanted`; the ones saved before the choice count as normal and either color). The next puzzle is one asked the current way, or the first of the pile when none is left, so a change made offline still leaves something to solve. A new batch is asked for when 3 or fewer are left asked that way, and the others are dropped only once more than 3 asked that way are kept, so a batch that brings only a few never empties the pile. Changing the choice asks for the mix at once when online, and a theme asks when it is opened. With none asked the current way, opening the puzzles waits for the batch, also one already on its way, and opens with what is kept if it cannot come; if the choice changes while a batch is on its way, it is asked again and whoever was waiting gets the new one. A puzzle left unsolved goes back to the pile, and any mate is accepted even when it is not the expected one. The daily puzzle reports nothing. Review mistakes uses the list Lichess keeps of the puzzles missed in the last 30 days and not solved since (`/api/puzzle/replay/30/mix`), so mistakes made on the site come too. The missed puzzles are fetched one by one, up to 10 at a time, into a pile of their own that works with no network and is also offered in the offline menu. Each fetch takes a second or two on a Kindle, so the review opens with the first puzzle it has and the rest arrive while the reader solves it; a second tap while it fetches asks nothing more, and leaving the online part ends the fetching. Each time the review opens online, the pile is brought in line with that list: what Lichess no longer lists leaves, and a result still waiting to be sent is not fetched again. A result goes to Lichess as any other, under the mix; on Lichess only the first attempt at a puzzle counts for the rating.

By opening, the list is the one Lichess has puzzles of (`/training/openings`, a page of the site that answers JSON when asked to, which its app also uses): 121 families, most puzzles first, with 706 variations in all, about 70 KB, asked once a session (`Puzzles.read_openings`, which leaves out a key that could not go into a path). The page opens at once with the last openings, whose puzzles are kept, and the list comes into it when it arrives, so with no network those can still be solved. A family with variations opens on them, with the whole family first; the names are Lichess's, in English, as on the site. An opening is an angle like a theme: its batch is asked by its key (`/api/puzzle/batch/Sicilian_Defense_Najdorf_Variation`) and its results go back under it. Since there are hundreds, only the last 5 opened keep a pile (`puzzle_openings_recent`, shown on top of the list), and the pile of one that falls off goes (`Puzzles.remember_opening`). An opening goes to the top only once its puzzles open, so a tap with no network takes no pile away, and a batch or a puzzle put back for an opening that fell off is let go (`Home:keeps_pile`), so its pile does not come back.

The history is the reader's puzzle activity (`/api/puzzle/activity`, one JSON per line, the last first), 30 at a time, each earlier page asked from the date of the last line (`before`), read or not, so a page of lines that cannot be played does not stop it. Each row has the rating of the puzzle, when it was tried and whether it was solved. A line has the position the reader moves in, the opponent's last move, the solution and the themes, so a puzzle opens to be solved again with no other request (`Puzzles.from_activity`, which leaves out a line that cannot be played; the last move is drawn from `last_uci`, since the position before it is not known). Its result goes to Lichess as any other, under the mix; it has no next puzzle and goes into no pile, even left unsolved (`single` in `PuzzleScreen`). Back from it, the page starts over, since Lichess puts the new try on top. The history is only online, and says so with no network.

## Puzzles in the package

For readers with no account, or no network, `puzzle_pack.lua` offers puzzles that come in the package, from the Lichess puzzle database (CC0), in `ink_knight/data/puzzles/<level>.lua`, one file for each level of the difficulty option. The repository has 10000 for each level, and `tools/package.sh` builds three zips with the first ones (`tools/puzzles/trim.lua`, which also writes `manifest.lua` with the count): `ink_knight.koplugin.zip`, the usual one, with 1000 for each level (5000 in all, 558 KB), and `ink_knight-20000-puzzles.koplugin.zip` and `ink_knight-50000-puzzles.koplugin.zip`, with 4000 and 10000 for each level (1.2 MB and 2.5 MB). The order is fixed, so the smaller packages have the first ones of the larger, and changing package keeps the progress; a place past the end of a level, after a change to a smaller package, starts over. The usual name stays the usual package, so the links and the device install (`docs/patterns/device_install`, which takes `dist/ink_knight.koplugin.zip` unless `PACKAGE` names another) keep working, and the release attaches every zip in `dist/`. With no account there is no puzzle rating to compare with, so each level is a fixed band of ratings: under 1000, 1000 to 1399, 1400 to 1799, 1800 to 2199, and 2200 or more. Only the file of the level played is read, when a puzzle opens, and the levels are let go when the plugin closes; the page itself reads only `manifest.lua`. On the Kindle 10 a level of the usual package takes 14 ms and 256 KB, and one of the largest package (10000 puzzles) about 180 ms and 2.4 MB. The database gives the position before the opponent's move, so these puzzles start from a FEN (`Puzzles.new_session` takes `fen` when there is one) and the opponent's move is played first, as with the others. The color option picks the puzzles where the reader plays that side. Each level goes on from where it stopped (`puzzle_pack` in the settings): a puzzle solved, or shown, moves the level on, one left unsolved comes again, and the end goes round to the start. Nothing is sent to Lichess, and the page says so. It opens from the offline menu, with the difficulty and the color, which are the same options as online but chosen here without the note about the Lichess rating and without asking Lichess for a batch. The row only shows when the package has the puzzles.

The selection is `tools/puzzles/build.lua`, reading the database uncompressed from the standard input (`zstd -dc <file> | luajit tools/puzzles/build.lua`): for each band, the puzzles with a settled rating (deviation up to 80), liked by most who rated them (popularity 80 or more), played at least 500 times, not marked very long and with up to 9 moves, ordered by the FNV-1a hash of their id (32 bits, checked against its reference values), a fixed shuffle, taking the first 10000 whose moves are all legal by the plugin's rules. The same database gives the same files byte for byte, the first ones did not change when the count went from 1000 to 4000 and to 10000, and `tests/puzzle_pack_spec.lua` solves every puzzle to the end with the puzzle rules (about 13 s on a Mac) and checks that a cut keeps the first ones. Lichess replaces the database every month under the same name, with no version to ask for, so the third-party data rule of a fixed source cannot hold: the files are generated by hand and reviewed, not again by the release, and `tools/puzzles/fetch_source.sh <empty folder>` downloads the database and stops if it is not the one recorded in `tools/puzzles/source.sha256` (2026-11-12, 6,193,530 puzzles). Updating the puzzles is a change of its own: `UPDATE=1`, build, review the difference and write the new checksum.

## Position editor

`editor.lua` and `ui/editor_screen.lua`, from the offline menu. A piece chosen from a palette (the twelve pieces and an eraser) goes on the square tapped, and the same piece again takes it away; the board shows the coordinates, whatever the option. The side to move is a button; the options are castling (only the rights the king and rooks in place allow, which leave by themselves when one of them moves away), the usual position, an empty board, turning the board, and a FEN pasted or typed in. Done checks the position (`Editor.problem`): one king a side, no pawn on the first or last rank, at most 16 pieces and 8 pawns a side, the side not to move not in check, and a side to move with a move left; otherwise it says why. A position that can be played can start a game against the engine, with the level and color chosen, or between two people, with or without a clock, and, with the online part open, the analysis of the review (`ReviewScreen.analyze`). The position is kept (`editor_fen`).

A game from a position keeps it (`initial_fen` in the saved game, a field added in 0.4.0, read back only while it is still a position that can be played), and plays, undoes, counts repetitions, writes the list of moves and plays again from there. Undo against the engine counts each side's moves from who moved first, which is black in a position set up with black to move (`Chess.take_back` with the first turn). The opening name stays out, since it is only for games from the usual start.

## Learn chess

The 18 stages for beginners of the official Lichess app, in four groups (the pieces, fundamentals, intermediate, advanced), 110 levels. `learn.lua` ports the model of the app (`lib/src/model/learn`, itself a port of the lessons of lichess.org), and `data/learn_stages.lua` its stages by hand, in the same order and with the same positions, stars, scripted moves and conditions, so the scores and stars match the site. The positions are often not chess: a lone piece and some stars, no king. The rules are the plugin's: with no king there is no check, so every move is legal, and the levels that let the reader blunder use `Chess.pseudo_legal_moves`, where a move into check fails the level and shows what attacks the king.

- **A level:** an enemy pawn stands under each star, unless the level says otherwise, so taking a star is a capture; the board draws the star and not the pawn. Taking every star finishes it, or the condition of the level does (give check, mate, castle, take every black piece, play the scenario). The opponent only moves in the scripted moves of a level, after a pause, or to show why a move failed: the capture of a piece left undefended, or a random move, after which the check mark follows the king (the app leaves it on the old square). A move that does not fail gives the turn back to the reader. The score counts stars, captures where they score (with the value of the piece in the stage about it) and scripted moves, plus a bonus by how many moves it took against the par; the stars of a level and of a stage come from it, as on the site.
- **The screen** (`ui/learn_screen.lua`) is the board with a banner of up to three lines on top for the goal, shrinking its text when needed, the stars and the hints drawn on the squares (arrows and circles; the colors of the app become grays, the warning ones black), the check marked, a rank bordered where a level points at it, and the level and score below. A level done says a word of praise from the app with its stars, and offers Retry and Next; a level failed says so and offers Retry. A stage never played opens with its introduction, and its end says what it taught, with its stars and the next stage. The first pawn level explains promotion when the pawn reaches the end, with the texts of the app. The best score of each level is kept (`learn_progress`), and the list shows the stars of each stage done, or how many levels. The progress in the offline menu is computed as on the site: each stage started counts 10, 8 or 5 points by its stars, its levels not done scoring nothing (`Learn.percent`).
- **The texts** are the app's, in English, Portuguese (Brazil) and Spanish (`data/learn_texts.lua`), generated by `tools/learn/build_texts.py` from the translation files of the app, downloaded at a fixed commit by `tools/learn/fetch_sources.sh <empty folder>` and checked against `tools/learn/sources.sha256`; the release builds them again and fails if they differ.
- **Drawing:** the size of the banner is worked out once for each goal, and a star is two glyphs, a white one over a larger black one, since the board redraws them on every move.
- **Checked:** `tests/learn_spec.lua` runs a search that proves most levels can be done in their par, with a small budget, and `luajit tools/learn/prove_levels.lua` the same with a large one: 108 of the 110 proven, none impossible, the two left being star levels with two pieces too wide for the search (rook 6 and bishop 6). The search found that the second pawn level is done in its par only by promoting to a knight, which is its point.

## Practice

The practice lessons of lichess.org (lichess.org/practice), as the official Lichess app carries them (`assets/practice.json`, which the app generates from the site): five sections of studies of chapters. Only what the engine of the plugin can judge comes in: of the 316 chapters, the 165 with a goal of mate, mate in so many moves or promotion, the 36 guided ones and the one commented game. The 114 judged by an evaluation ("reach +2 in 3 moves", or hold a draw) need an engine as strong as Stockfish, which the app uses, and are left out, and so are the 5 tactics studies that had nothing else, so 27 studies of the 32 remain.

- **The data** (`data/practice.lua`, 48 KB) is generated by `luajit tools/practice/build.lua <folder>` from the file of the app, downloaded at a fixed commit (the one of the texts of Learn chess) by `tools/practice/fetch_sources.sh <empty folder>` and checked against `tools/practice/sources.sha256`. The moves of the guided chapters are read with the rules of the plugin, so a move it cannot read stops the build, and a comment at the start of a variation goes to its first move; each one keeps its main line in UCI, the drawings after each move (arrows and circles, as the PGN writes them) and the reader's moves off the line the author foresaw, with their drawings. The texts go to `data/practice_texts_en.lua` (62 KB), keyed by chapter and what they are (`.n` name, `.d` description, `.c<ply>` comment after a move, `.w<ply>.<move>` comment on a wrong move, `.h<ply>` hint, `.v<ply>` comment for any wrong move, with the plies as the app indexes them), without drawing commands, links (a [text](address) keeps its text), soft hyphens or the two dashes of the source, said another way (`REWORDS`, where a new one stops the build). The release builds both again and fails if they differ.
- **The texts** of the chapters exist only in English on Lichess. `data/practice_texts_pt.lua` and `data/practice_texts_es.lua` are translated by hand from the English file (decision of 2026-11-12), with the terms of Lichess in each language, the moves and squares as they are and no dash; a text missing in a translation shows in English. When the English file changes, the same keys change in both. The names of the sections and studies are the app's, in the three languages, generated with the texts of Learn chess into `data/learn_texts.lua` (`practice*` keys).
- **A chapter with a goal** (`practice.lua`) is played against the engine (`Practice.ENGINE`: up to 2 s, depth 3, no noise, captures searched past the depth), which also makes the first move of a chapter that starts with the opponent. As in the app (`practice_goal.dart`), a mate by the reader solves it and one by the opponent fails it; a stalemate or a dead draw fails it, and so does the same position a third time, except in a chapter to promote; the fifty-move rule does not apply, since a long mate may need more; a mate in so many moves fails once the reader's moves are spent without mate; a promotion is judged on the engine's score of the position after it, against the target of Lichess, which is for white (so negative in a chapter played as black). What the app judges with Stockfish on the way (a move that throws the win away, a mate no longer reachable in the moves left) is left out: the chapter goes on until the rules or the count decide it. Hint asks the engine (`Engine.HINT`) and draws its move.
- **A guided chapter** is the app's gamebook (`practice_gamebook_controller.dart`). One with a description opens with it on a page, and its opponent waits for the page to close; Read shows it again, before the text of the banner. These pages have the name of the study as title and the chapter's, which can be long, on top of the text. The reader finds the author's moves; the opponent's come by themselves after a second (0.3 s at the start), unless there is a comment to read, which waits for Continue; a wrong move is shown and taken back after a moment, or, with a comment, on Continue. The comment of a wrong move is the author's for that move, or the one for any move played instead of theirs. Hint shows the author's hint where there is one, and Solution draws the move. The end of the line completes it.
- **The commented game** is gone through with `<` and `>`, or `>>` to the next comment; its end counts it done.
- **The screen** (`ui/practice_screen.lua`) is the board with a banner of four lines on top (`banner_lines = 4`): the description of the chapter or the comment on the board, shrinking from 19 to 13 points to fit, and Read (`BoardScreen:banner_fits`) to read the whole of it on a page when even 13 does not fit. Below the board, the name of the chapter, or of the study when the chapter's is too long for the bar (`BoardScreen:bar_name_fits`), and its place in the study; then the goal, with the move count of a mate in so many moves, or what just happened. Next goes to the next chapter, solved or not, as in the app; after the last one, a page says how many of the study are done and offers the next study.
- **Progress** keeps the fewest moves of each chapter done, by id (`practice_progress`, as the app keeps it), and the offline menu shows the share of chapters done, rounded down as on the site. A study opens on its list of chapters, which wrap their long names (`wrap` in a row of a page), the first one not done in bold, and the list of studies shows how many of each are done.
- **Checked:** `tests/practice_spec.lua` checks the data (every line, wrong move and drawing playable and drawable, the mates in one and two forced, by the side the reader plays), that every text belongs to a chapter and that both translations have the same texts, naming the same squares and with no dash, and the rules of the goals and of the guided chapters.

## Clocks

`chess_clock.lua` is a clock with an increment, given the time by its caller so the tests move it: one side runs, a press stops it with the increment added and starts the other, it can pause and resume, a side at zero is flagged and stays so, and it is saved paused. The presets are the ones Lichess writes, from 3+2 to 30+20; the last one chosen is kept and marked (`clock_preset`, "none" for a game without one, and the mark at the start). Each redraw is scheduled for when the time shown changes, the rest of the current second, so the delay of the timers does not pile up and skip a second.

- **The game between two people** can have one, chosen before it starts ("No clock" first). It starts with black's time after white's first move, as the first move costs nothing on Lichess either. The times are in the clock boxes of the bars, the side to move inverted, and each second only the bars change, with `fast`. Pause stops the time and the moves, and is kept with the game, so continuing a paused game does not start its clock. The clock stops while the screen is closed or the device sleeps, and starts again when the game is continued or the sleep screen is gone; the game is saved with it (`clock`, `clock_preset` and `clock_paused` in `two_player_game`, fields added in 0.4.0, so older saves have no clock). Undo keeps the time spent, takes back the increment the move had added, so undo and move again gain nothing, and gives the clock to the side to move again, also after undoing a mate; back at the start the clock is as new. A side out of time loses, unless the other side has nothing left to mate with (`Chess.can_mate`: a lone king, or a king and one minor piece against a lone king), which is a draw; there is no undo after a flag. The device stays awake while it runs (`awake.lua`, with the game as its holder), as in a game on Lichess with a clock.
- **The chess clock** (`ui/clock_screen.lua`) is for a game on a physical board, with the device lying between the players. The screen is two halves with the buttons between them, the top half drawn on its own buffer and turned round with `rotate(180)` so the player across reads it the right way up. Each player taps their own half after moving; the first tap starts the other side's clock and is not a move, as on a physical clock, where black starts white's clock before the first move. The half thinking is inverted, so it shows from afar, with the moves of each side counted. Each second only that half is sent to the display, with `fast`; a turn sends both, counted by `refresh.lua` for a flash every 20. The sizes that fit (a time measured by its length) and the buffer of the turned half are kept, so a second costs no measuring and no new buffer: on the Kindle 10, 2 ms to draw the bottom half and 6 ms for the top one, turned round. It keeps the device awake while it runs; asleep, it pauses and waits for Continue, since the players cannot see it. Leaving or restarting while it runs asks first; after a flag, restarting does not.

## Coordinate training

`coordinates.lua` and `ui/coordinates_screen.lua`, from the offline menu, follow the trainer of Lichess and of its app: find the square named, or name the square marked among four names, as many as possible in 30 seconds or with no limit, from the white side, the black side or one drawn. A wrong answer keeps the same square and says which square or name it was, so a second wrong tap still changes the screen, a square is never asked twice in a row, and the four names are in alphabetical order, so where the right one is says nothing. The board is drawn without coordinates whatever the option, with or without the pieces of the start. The square to find shows large in the clock box of the top bar, and the time in the one of the bottom bar, so each second only the bars change, with `fast`, as the clocks of a game. The names to choose from are the buttons. The run waits while the device sleeps, with the time it had, and goes on after waking up, only once the sleep screen is gone when it waits for a tap. The last tick comes when the time runs out rather than on the next second, and an answer after the time ends the run instead of scoring. A side drawn at random is drawn when the screen opens and again only for the next run, so the board does not turn on Start. The best score in 30 seconds of each mode and side is kept (`coordinate_records`) and shown on the page; a run with no limit ends with Stop and keeps no best.

## Saved state

Everything is in `koreader/settings/ink_knight.lua`, apart from the token (see above): the options, the games without internet (`offline_game` and `two_player_game`, this one with its clock, each separate, so a damaged game never takes the options with it), the piles of puzzles (with the last openings whose puzzles were opened, `puzzle_openings_recent`), the results waiting to be sent and the correspondence games kept offline (`correspondence`, with the account they belong to, removed when the token is), where each level of the puzzles in the package goes on (`puzzle_pack`), the best scores of the coordinate training (`coordinate_records`) and of each level of Learn chess (`learn_progress`), the practice chapters done (`practice_progress`), and the position of the editor (`editor_fen`). It is written after each change, not only on closing. `state.lua` reads it back through `saved_state.lua` (pattern saved_state): an option that no longer exists gets its default, a game must still be legal move by move from the start or it is dropped and the menu stops offering it, and a puzzle or result with a missing part is left out. Games carry `version = 1`; the ones saved before the field, by 0.2.0, have the same format and are read as version 1. `tests/saves/0.2.0.lua` is a real save written by 0.2.0 in the emulator, and `tests/state_spec.lua` reads it back with everything it had. Uninstalling means removing that file and `settings/ink_knight_token` or, on a Kindle, `/var/local/ink_knight`.

## Correspondence without internet

The list of games (`/api/account/playing`) has the whole position of each game as a FEN, with castling and en passant, so a correspondence game can be shown and played offline from it, without opening its stream first. Each time the list comes, `correspondence.lua` keeps the standard correspondence games, with the opponent, the last move and the time left, and forgets the ones no longer listed; the list asks for 50 games, the most Lichess gives, so with 50 nothing is forgotten for being missing. They show in the offline menu, the reader's turn first, with how long ago Lichess sent them. `ui/correspondence_screen.lua` opens one: on the reader's turn a legal move can be made, and it waits with the position it was made in, can be taken back, and blocks a second move. The reader's clock counts down only on the reader's turn, from when the list came.

Moves waiting go out the next time the list comes online, before it replaces the kept positions: only when the game is still listed, it is still the reader's turn and the position is the same (board, side to move, castling and en passant, `Chess.epd`). A game that already shows the move played had received it, with the answer lost on the way back, and counts as sent. Otherwise, for instance after the opponent resigned, a takeback or a move made on the site, the move is dropped and the reader is told, by the opponent's name. A move refused by Lichess (400) is dropped the same way; a network failure keeps it for next time. After sending, the list is asked again. A move made on the kept board while the online part is open goes out at once, and the board shows the result. Without `board:play` the moves stay saved and the reader is told once a session. A move made in the online game replaces one waiting for the same game, and the kept games are read in full only when that game has one. The kept games are written only when something changed: a position that did not change keeps the clock of the first list that had it. With 50 games or more listed, a kept game missing from the list stays, since it may only be beyond the limit, so a finished game can linger for readers with that many. The moves of the game are not kept, only the position, so the list of moves is not offered offline. The official app does the same with the site's protocol (`model/correspondence` in `lichess-org/mobile`); here the move goes through the board API.

## Offline engine

`engine.lua` is a negamax with alpha-beta and iterative deepening, valued by material with small rewards for the center and for advancing pawns. It is a coroutine: `offline_game` runs it for 40 ms at a time and gives the screen its turn, which is what froze the screen in earlier clients. Each of the 4 levels has a time limit, a depth and an amount of noise, and noise never throws away a forced mate. The game is saved after each move, and draws by repetition, the fifty-move rule and insufficient material are checked here, since no server does it. The reader picks a color, or lets it be drawn, and playing again keeps that choice. Undo goes back to the reader's last move, taking the computer's answer with it and stopping a search under way, and works after a mate too, but not after resigning. A hint runs the same search with `Engine.HINT` (3 seconds, depth 3, no noise), so it is the best move found and not a weaker one, marks the piece and its square, so a tap there plays it, and names the move below the board. Here it is not cheating, since no server is involved. The same screen plays a game between two people on one device: no engine, whoever is to move plays, undo takes back one move, a button turns the board and the way it faces is saved, resigning is for the side to move, and the game is kept under its own key, apart from the one against the engine.

## Analysis of an offline game

Once a game without internet is over, Analyze (`game_review.lua`) goes through its moves with the engine, a search each (`GameReview.LIMITS`: up to 2.5 s and depth 3, no noise, and past that depth up to four captures, so a line does not end in the middle of an exchange and a defended piece taken is not counted as won; on the Kindle 10 depth 3 takes 0.3 to 1.5 s, so the depth is the limit there too), in slices like the engine's own moves, with the progress below the board and a way to cancel; against the engine only the reader's moves, and never a move that was the only legal one. The engine reports the best move and its score, and the exact score of the move played, searched in full where the others are only shown worse (`Engine.search` with `report` and `exact`). A loss of a pawn and a half or more is a mistake and of three pawns a blunder; walking into a mate is a blunder, and missing one is a mistake while the game stays won. The score shown is the one of the position after the move, mates counted from there. A move whose search finished no depth, as after a sleep in the middle, is searched once more and otherwise left out, and the notice says how many; a game with no move of the reader to look at says so instead of opening an empty review. The review is numbered from the move number of the FEN. The engine is small and shallow, so smaller losses are left out, which the notice that opens with the review does not hide. The review is the one of Lichess games (`ReviewScreen`), from the position the game started at, with the score of each move as Lichess writes it, the mark and the better move; the analysis of Lichess is only offered with the online part open. The result is kept while the screen is open, so a second tap opens the same review, and a move taken back throws it away.

## Token page

`ui/token_screen.lua`, with `token_access.lua`, receives the token from another device on the same network. The session (code, address, private networks, firewall) is `lan.lua`, and the server `http_server.lua` (pattern lan_server); `token_access.lua` decides what each request gets. None of them makes the connection fully secure: there is no HTTPS, so someone capturing traffic on the same network could see the token. That is why the screen asks for a trusted network.

| Layer | What it does |
|---|---|
| Only on while in use | The server exists while the screen is open, and stops on Cancel, after a token arrives and after 5 minutes without use. Asleep, the Wi-Fi goes, so the session ends at once and the screen says so when the device wakes up |
| Firewall | The port (8644) opens in `iptables` only after the server is up, and only for 10.x, 172.16-31.x and 192.168.x. It is listed in `settings/ink_knight.firewall` before the first rule, so a crash with the page open is undone when KOReader starts again |
| Secret code | The address carries a random code from `/dev/urandom`, new at each opening. Without it, every answer is the same 404 |
| Approval on the device | The first device with the code must be approved on the screen, and no form is shown before that |
| One device | Once approved, no other address is served |
| Private networks only | It refuses to start outside 10.x, 172.16-31.x and 192.168.x, and refuses clients from outside |
| `Host` and `Origin` | Block DNS rebinding and other sites posting to the page |
| Limits | Headers up to 8 KB, and the body of the form, up to 512 bytes, is only read after the code, the `Host`, the approval and the `Origin` are checked. Up to 12 connections, 6 of them kept for the approved device and at most 2 for any other address, 10 seconds for a request and 30 without progress. 20 invalid requests block that address |
| Token | Must have the shape of a Lichess token, is never echoed in a page and is never logged |
| Pages | No script, a restrictive `Content-Security-Policy`, `nosniff`, no frames and no cache |

## How to publish a version

1. Update `version` in `_meta.lua` and create the version's section in `CHANGELOG.md`.
2. Run `sh tools/check.sh`, the checks in the emulator above, and try it on a device.
3. Publish the release on GitHub, creating the `v<version>` tag with it. The `release.yml` workflow checks that the tag matches `_meta.lua`, runs `tools/check.sh release`, builds the package and attaches every zip in `dist/` with its checksum. The CI runs `tools/check.sh` on every push.
